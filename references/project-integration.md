# 项目接入指南

这份全局 `testing-workflow` skill 解决的是“怎么做测试治理”，不是“某个项目具体怎么测”。

如果你想把它接到自己的项目里，推荐采用双层结构：

## 1. 全局 skill 负责什么

全局 skill 负责：

- 六步测试治理流程
- 风险分级方法
- 多智能体协作规则
- 输出目录和轮次协议
- bad case 沉淀方法

## 2. 项目级 skill 负责什么

项目级 skill 负责：

- 具体测试命令
- 具体环境切换规则
- 项目特有风险链路
- 项目特有黄金断言
- 项目特有自动化入口
- 项目特有回归包

## 3. 推荐接法

先用全局 `testing-workflow` 做：

- 意图识别
- 影响面分析
- 风险建模
- 路径规划

然后切到项目级 skill 去补：

- 在这个项目里具体执行哪些命令
- 该在哪个环境验收
- 哪些链路属于项目的 P0 / P1
- 哪些断言和历史 bad case 必须覆盖

## 4. 项目级 skill 至少应补哪些内容

建议项目级 skill 至少包含：

1. 风险链路清单
2. 测试命令矩阵
3. 环境选择规则
4. 黄金断言
5. 历史 bad case 回归包
6. 测试环境运行边界

## 5. 协作边界

不要让全局 skill 直接硬编码项目命令、服务器、模块名、环境地址。

不要让项目级 skill 重复定义全局流程、反模式和多智能体原则。

推荐做法是：

- 全局 skill 管方法
- 项目级 skill 管事实

其中“测试环境运行边界”建议项目级 skill 明确写清：

- 哪些环境是常驻、受管环境
- 验收时默认是只读核对，还是允许自动重启
- 哪些脚本属于“代码同步/发布”动作
- 哪些脚本属于“环境维护”动作
- 什么时候必须先暂停测试、转为环境修复任务

如果项目已经有专门的测试服务器，默认应把它视为“受管常驻环境”：

- 正式验收默认先核对现状和健康度
- 不要为了完成一次验收，临时手工拉起一套开发态服务
- 如果需要重启、重建、补迁移、改 nginx 或改托管方式，应把它显式当成单独的环境维护任务记录

## 6. 最终效果

理想状态下，一次完整测试会是：

1. 全局 skill 定义方法和输出结构
2. 项目级 skill 补全具体执行路径
3. 测试产出写入 `testing-artifacts/<task-id>/<round-id>/`
4. 新 bad case 反哺项目级 skill 和回归资产
