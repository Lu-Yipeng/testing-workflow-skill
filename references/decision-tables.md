# 决策表

## 1. 是否需要完整六步流程

| 条件 | 动作 |
|---|---|
| 低风险、局部修复 | 可简化，但仍应记录 intent / execution / eval |
| 涉及共享逻辑、状态机、权限、支付、数据完整性 | 必须走完整六步 |
| 发布前验证或跨系统联动 | 必须走完整六步 |

## 2. 是否默认开启双 Agent

| 条件 | 动作 |
|---|---|
| 用户明确要求双 Agent / 多 Agent | 若工具可用，默认开启 |
| 跨 2 个以上系统或验证层 | 若工具可用，默认开启 |
| 需要一边建模风险一边并行执行 | 若工具可用，默认开启 |
| 任务局部且执行路径明显 | 不开 |

## 3. 是否允许探索式测试作为主体

| 条件 | 动作 |
|---|---|
| P0 风险链路 | 不允许以探索替代定向验证 |
| P1 风险链路 | 探索只能作为补充 |
| 新功能早期、需求边界不清 | 可用探索发现问题，但不能单独形成最终结论 |

## 4. 是否需要项目级技能或项目文档补充

| 条件 | 动作 |
|---|---|
| 需要知道具体脚本、环境、服务名 | 必须查项目级 skill 或仓库文档 |
| 只是在做通用测试治理设计 | 全局 skill 足够 |

## 5. 是否需要新增轮次

| 条件 | 动作 |
|---|---|
| 只是补充说明，未重新执行 | 不新增轮次 |
| 补跑任何测试或改变验证路径 | 新增轮次 |
| 环境变化导致重测 | 新增轮次 |

## 6. 有 PRD 时如何提炼测试任务

| 条件 | 动作 |
|---|---|
| PRD 明确给出主流程 | 抽取为主链路测试 |
| PRD 明确给出角色差异 | 为每个角色建立独立验证项 |
| PRD 明确给出状态变化 | 建立状态迁移断言 |
| PRD 明确给出异常或不支持项 | 建立边界 / 非目标验证项 |
| PRD 只有目标没有步骤 | 结合代码和页面补全路径，但要标明哪些步骤来自推断 |

## 7. 没有完整 PRD 时如何反推测试范围

| 条件 | 动作 |
|---|---|
| 有页面可访问 | 从页面主按钮、主列表、主表单反推主链路 |
| 有代码可读 | 从 router / controller / API client / store 反推动作与状态 |
| 有历史测试资产 | 优先继承已有主链路和高频 bad case |
| 只有现网行为可观察 | 先记录当前行为基线，再做最小有意义验证 |
| 多个事实源互相矛盾 | 明确标记冲突，不隐式假设其中一方绝对正确 |

## 8. PRD、代码、现网行为冲突时如何判定

| 条件 | 动作 |
|---|---|
| PRD 新、代码旧、现网与代码一致 | 记录为“实现未跟上需求”，按风险决定是否阻塞 |
| PRD 旧、代码与现网一致 | 优先视为文档过期，记录并建议更新 PRD |
| 代码与现网不一致 | 优先排查环境、配置、发布漂移 |
| 三者都不一致 | 明确记录冲突，暂停给出强通过结论，升级给产品 / 开发确认 |
| 无法当场确认正确口径 | 在测试产物里显式写明“暂定事实源”和未决问题 |
