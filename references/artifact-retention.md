# 测试产物提交与保留策略

这份文档回答一个很现实的问题：

`testing-artifacts/` 下面生成的内容，到底哪些该提交，哪些不该提交？

## 基本原则

1. 能帮助团队复盘、比较轮次、沉淀规则的内容，优先保留
2. 只对单次调试有意义、体积大、噪声高的内容，不要默认提交
3. 结论性文档优先进入版本管理；原始大体积证据优先做外部保留或临时保留

## 建议提交的内容

默认建议提交：

- `01-intent.md`
- `02-impact.md`
- `03-risk.md`
- `04-plan.md`
- `06-eval.md`
- `07-knowledge-capture.md`
- `planner-handoff.md`
- `executor-report.md`

这些文件的价值在于：

- 可回放
- 可比较
- 可沉淀团队共识
- 可反哺项目级 skill 和回归资产

## 视情况提交的内容

以下内容按项目习惯决定是否提交：

- `05-execution.md`

如果该文件主要记录：

- 执行过哪些步骤
- 哪些测试通过 / 失败
- 哪些路径需要补轮次

则可以提交。

如果该文件塞入了大量一次性的原始命令输出、冗长日志、临时调试备注，则建议只保留摘要，把大段原始输出移到外部附件或单独日志文件。

## 不建议默认提交的内容

以下内容不建议直接塞进版本库：

- 大体积截图
- 录屏
- 浏览器 trace
- 原始测试日志全文
- 临时导出的接口大 JSON
- 本地环境特有的路径和缓存文件

这些内容更适合：

- 放在 CI / 测试平台产物里
- 放在对象存储或共享目录里
- 在文档中只保留路径或链接

## 推荐做法

推荐把测试产物分成两层：

### 1. 结构化结论文档

放在：

- `testing-artifacts/<task-id>/<round-id>/`

这部分适合进版本库。

### 2. 原始证据

放在：

- CI 产物
- 外部附件目录
- 项目自定义的 `artifacts/`、`tmp/`、对象存储等位置

在文档里记录它们的路径、链接或摘要，而不是把大体积文件直接提交。

## 团队协作建议

如果团队刚开始使用这套工作流，建议先采用保守策略：

- 先提交结论文档
- 不提交大体积原始证据
- 每两周回看一次哪些文件真正有复用价值

## 与项目级 skill 的关系

全局 skill 只给出通用提交建议。

如果某个项目有自己的要求，例如：

- 正式验收文档必须提交
- 失败截图统一走 CI 产物
- 某类日志必须脱敏后保存

则应由项目级 skill 明确覆盖这些细节。
