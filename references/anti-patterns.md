# 反模式

这个 skill 围绕两个重要约束建立。

## 反模式 1：围着 Benchmark 优化

Benchmark 的用途可以是：

- 建立能力基线
- 发现大范围能力退化

但它们不应成为质量改进迭代的主燃料。

### 为什么

1. 它们容易诱导过拟合。
2. 它们和真实生产成功率常常相关性很弱。
3. 它们会分散对真正重要失败模式的注意力。

### 更好的迭代燃料

优先使用：

- 真实漏测缺陷
- 生产或预发失败样本
- 重复出现的 bad case
- 具体工作流的回归案例

## 反模式 2：默认走纯探索

纯探索式测试不应成为默认骨架。

### 为什么

1. 开放探索会漏掉很多“肉眼看不见”的失败。
2. 没有边界的智能体很容易跑偏。
3. 人类协作者需要明确范围和明确结论。

### 更好的默认方式

优先采用：

`instruction-driven testing + domain knowledge + bounded execution`

探索仍然可以作为补充，适用于：

- 早期产品探索
- 长尾 UI 检查
- 需求定义不够严格的工作流

但它不应替代高风险链路上的定向验证。
