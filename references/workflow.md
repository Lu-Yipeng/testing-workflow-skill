# 六步工作流

## 1. 意图识别

先明确你需要哪一种“信心”。

可用问题：

- 哪个行为必须继续成立？
- 我们最担心哪种回归？
- 这是验收、回归、发布前信心检查，还是诊断问题？

如果存在 PRD、需求单、交互稿或验收标准，先从这些材料提炼：

- 目标用户是谁
- 用户要完成什么动作
- 哪些结果被定义为成功
- 哪些状态变化被定义为关键
- 哪些边界或异常分支被显式提到

把 PRD 里的内容改写成测试任务时，优先转成下面几类：

- 主链路任务：用户从起点走到目标结果
- 角色任务：不同角色是否各自可达正确路径
- 状态任务：关键状态是否正确流转
- 边界任务：超时、失败、空态、重复提交、权限不符
- 非目标任务：PRD 明确说“不支持”或“阶段性不做”的边界

## 2. 影响面分析

映射受影响面：

- 模块
- 接口
- 角色
- 状态迁移
- UI 面
- 环境

如果没有完整 PRD，不要停止测试设计，而是从下面几类事实源反推：

- 代码入口：router、controller、service、API client、store
- 页面结构：导航、按钮、表单、详情页、结果页
- 历史行为：已有测试用例、历史测试产物、bad case、线上工单
- 契约事实：接口字段、状态枚举、数据库主状态源

推荐反推顺序：

1. 找入口页和主动作
2. 找动作对应 API
3. 找 API 对应状态变化
4. 找状态变化投影到哪些页面或角色
5. 找历史上最容易坏的边界

## 3. 风险建模

用影响范围和可逆性来估算测试深度。

重点问：

- 如果这里坏了，谁会先发现？
- 这个问题会不会损失金钱、数据、信任或可用性？
- 是否存在跨系统耦合？

如果 PRD、代码、现网行为彼此不一致，不要直接替任何一方做隐式裁决。
应先把冲突识别为测试对象的一部分。

至少记录：

- PRD 期望是什么
- 代码当前实现是什么
- 现网或测试环境实际表现是什么
- 这三者中哪个是本轮暂定事实源
- 为什么这样判定

## 4. 路径规划

构建“最小但有意义”的验证路径：

- 主链路
- 边界或失败路径
- 自动化检查
- 人工检查
- 环境选择

若有 PRD，路径规划应优先覆盖：

- PRD 明确承诺的主链路
- PRD 明确写出的约束和不支持项
- PRD 未明说但由主状态变化自然推出的失败分支

若没有完整 PRD，路径规划应优先覆盖：

- 当前页面上最主要的用户动作
- 代码里最明显的状态迁移
- 历史 bad case 集中区域
- 最容易对用户造成错误感知的结果页

## 5. 精确执行

执行时边界要清楚：

- 成功标准
- 停止条件
- 证据收集

## 6. 评估与知识沉淀

结束时至少要判断：

- 哪些内容应该变成回归用例
- 哪些内容应该变成 checklist
- 哪些内容应该沉淀为项目专属风险

如果本轮存在“PRD / 代码 / 现网行为冲突”，评估阶段必须单独收口：

- 冲突是否已被产品、研发或测试确认
- 本轮测试结论依赖的是哪一个事实源
- 这是需求漂移、实现偏差，还是文档过期
- 后续应该更新 PRD、修代码，还是补环境说明
